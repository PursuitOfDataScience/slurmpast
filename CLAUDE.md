# Working on slurmpast

Repository: `PursuitOfDataScience/slurmpast`.

## Reporting bugs: one issue per audit, not one per bug

When an audit, review, or ordinary piece of work turns up defects, **file them as a
single GitHub issue on the repository the code belongs to** — here,
`PursuitOfDataScience/slurmpast`.

**All the bugs found in one pass go in that one issue.** Do not open an issue per
finding. A ten-finding sweep is one issue with ten sections, ranked worst first. Ten
separate issues fragment a single review into a queue nobody reads in order, hide
which defects share a root cause, and lose the ranking that says what to fix first.

Applies whether the work was asked for as "find bugs", "review this", or was
incidental to another task.

### Confirm before you file

An issue is public and permanent, so a claim in one has to be right. Before a
finding goes in:

* **Reproduce it by running the code**, not by reading it. This repo settled on that
  in round three of `issues.md`: "each was reproduced by running the code before
  being written down." A finding you can only argue for is a hypothesis.
* **Re-verify the whole list once more before filing.** Findings that do not survive
  the second pass get **withdrawn or narrowed, and said so in the issue** — an audit
  that quietly drops its wrong claims is not one that can be trusted about the rest.
* **Check it is not already known.** Search the open issues, and read `issues.md`:
  four audit rounds are recorded there, including items decided "not a defect" or
  "by design", and two deliberately left Open.
* **Check whether a test already pins the behaviour.** If a test asserts it, the
  behaviour is intended until argued otherwise — say so and argue it, rather than
  reporting it as an oversight. If no test covers it, say that too; this suite's
  recurring failure mode is "tests that assert less than they appear to."

### What each finding needs

* `file.py:line` for the site.
* The reproduction — the command or the few lines that trigger it, and its actual
  output. Paste real output, not a description of it.
* What the reader gets versus what they should get, and why it matters. Prefer the
  repo's own documented intent as the standard: much of this codebase explains in
  comments why a thing is done a certain way, and the strongest findings are the
  ones where the code has drifted from a rule it states about itself.
* Severity ordering across the issue, worst first.

State plainly what was verified and what was not, and keep code-defects, documentation
defects and minor nits in separate sections so a reader can act on the first without
wading through the last.

### Filing

* One issue, titled with the count and the headline defects, not "Bugs found".
* Say up front how the code was evaluated and whether the test suite passes, so a
  reader knows the findings are gaps rather than regressions.
* End every issue, comment and review body with the attribution footer:

  ```
  ---
  _Generated by [Claude Code](https://claude.ai/code)_
  ```

* Filing the issue is the deliverable. Do not also change code unless asked — offer
  to, and let the maintainer choose the scope.

## Development

* Develop on the branch named in the task; commit and push there, never to `main`.
* `ruff`, `ruff format` and `mypy` must stay clean (config in `pyproject.toml`).
* Tests live in `tests/`, run with `pytest`. A fix ships with a test and its control.
* The analysis modules (`sacct`, `model`, `diagnose`, `patterns`, `nodes`, `index`,
  `sizing`, `logs`, `site`, `duration`) import no third-party package — keep it that
  way. Only `render`, `report` and `tui` may touch `rich`/`textual`.
* `render.py` exists so the dashboard and `--plain` cannot drift. A change to one
  surface that the other also draws belongs in `render.py`, not in both.
